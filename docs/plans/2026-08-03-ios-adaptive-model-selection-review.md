## Findings

### F1 — major — `os_proc_available_memory()` returns 0 on Simulator; the plan's Simulator story only covers `physicalMemory`

Decision 1's rationale and risk 1 say the Simulator number is "structurally
wrong" because `physicalMemory` reports host RAM. True — but the plan's
*headline* signal, `availableMemoryBytes` via `os_proc_available_memory()`,
returns **0 on the Simulator** (the jetsam/memorystatus budget does not exist
there; same on Mac Catalyst). So in the only environment this project
validates, the "number that actually predicts a jetsam kill" reads zero, and
naive policy code would mark every model unrunnable. The iOS-A bridge-harness
test "probe module returns well-formed values" will meet this immediately.
Availability (iOS 13+, deployment target 17.0) is fine.

**Corrections:** (a) define `availableMemoryBytes == 0` ⇒ "unknown", policy
falls back to `physicalMemory`-with-advisory-label; (b) add a harness assertion
pinning the 0-on-Simulator behavior so the fallback is exercised, and extend
risk 1 to cover it.

### F2 — major — iOS-B imports Android M9's owned-partial state model into an API that doesn't provide an owned partial

iOS-B persists "partial length … plus HTTP validators" and resumes "via
`resumeData` where the system supplies it, and HTTP `Range` + `If-Range`
otherwise" — a direct lift of M9's OkHttp append-to-owned-file design. On iOS
with `URLSessionConfiguration.background`: only download/upload tasks are
permitted (no data tasks); a download task writes to a **system-owned temp
file** you never see until `didFinishDownloadingTo`; `resumeData` is an opaque
blob referencing system temp state, not "partial length" you can persist or
hash. The custom-Range fallback therefore means: issue a new download task with
a `Range` header, receive the *suffix* as a separate temp file, and concatenate
onto an app-owned partial — a design the plan never describes, and the only
path in which "partial length" is a meaningful durable field.

Additionally, HF-specific: `sourceUrl` (pinned `resolve/<sha>` form,
`catalog.ts:158-163`) 302-redirects to a signed CDN URL; stale `resumeData` can
embed the expired signed URL and fail with 403 on resume — must be handled like
a validator mismatch (restart from original URL). HF CDN Range support itself
could not be verified from the review environment.

**Corrections:** pick and specify one state model — (a) `resumeData`-primary:
persist the opaque blob, treat "partial length" as unavailable, hash the final
delivered file (validators still checked); or (b) app-owned partial with
Range-suffix download tasks and explicit concatenation (keeps M9's field set);
add the 403-on-resume case to the failure matrix either way.

### F3 — major — `handleEventsForBackgroundURLSession` "wired in the app delegate" ignores this repo's prebuild convention

`app/ios/PocketLM/AppDelegate.swift` is the stock Expo template (committed, no
background-session hook), regenerated by `prebuild --clean`; the repo's stated
convention for surviving prebuild is config plugins
(`app/plugins/withPocketLMPod.js` header comment says exactly this, and the
Android plan's M6 gate assumes clean prebuilds). Expo forwards
`handleEventsForBackgroundURLSession` only to registered
`ExpoAppDelegateSubscriber`s
(`expo-modules-core/ios/AppDelegates/ExpoAppDelegateSubscriberManager.swift:165-187`)
— and `PocketLMNative` is a bare CocoaPod TurboModule, not an Expo module, so
it cannot receive the callback as-is.

**Corrections:** name the mechanism in the plan: (a) a small Expo-module
subscriber shim that hands the completion handler to the downloader; or (b) a
config-plugin AppDelegate mod (`withAppDelegate` dangerous-mod, documented as
such); or (c) an explicit "AppDelegate is hand-maintained; `prebuild --clean`
is out of policy" statement. Any of the three is fine; silence is not.

### F4 — major — "separate TurboModule; frozen `PocketLMSpec` is not touched" is only half true under this codegen setup

`app/package.json:73-80` declares one codegen unit named `PocketLMSpec` with
`jsSrcsDir: "src/lib"`. Any probe spec (`NativePocketLMDeviceProbe.ts`) must
live in a scanned `jsSrcsDir`, and codegen regenerates the **same
`PocketLMSpec` library/header** with an added protocol — the frozen thing is
the PocketLM module *contract*, not the generated artifact the podspec consumes
(`PocketLMNative.podspec:93-101`). The plan also never says where the spec file
lives, and that answer differs by branch: Android-proceeds, M6 has moved
`codegenConfig` + specs into the workspace library, so the probe spec must land
there (the Android plan is equally silent — an inherited gap, but this plan
repeats it); Android-dropped, it lands in `app/src/lib`. Registration
(`RCT_EXPORT_MODULE`) and the `Bridge/*.{h,m,mm}` source glob do absorb the new
`.mm` automatically — that part is fine.

**Corrections:** restate as "the PocketLM module contract is untouched; the
generated `PocketLMSpec` artifact gains a probe protocol"; specify the spec
file's home in both branches; note the protocol's "one coherently registered
`PocketLM` TurboModule" clause (`INFERENCE_PROTOCOL_V2.md:220`) is about the
PocketLM module and permits a sibling — cite it to preempt the objection.

### F5 — major — iOS-0 is under-priced and mis-ordered

iOS-0 is priced at 2–2.5 weeks — exactly the parent's M8 estimate. But iOS-0 =
M8's shared portion (nearly all of M8; only the ~100-line Kotlin probe and
Android UI glue drop out) **plus** M9's `pocketlm_verify_model` lift, which
inside M9 carries an ABI version bump, header-compile tests, and Catch2
coverage including a structurally-valid-wrong-metadata GGUF fixture — several
days of work the parent prices inside M9's 2–3 weeks. Net: iOS-0 ≈ 2.5–3+
weeks, and the iOS-only total ≈ 6.5–9 weeks. Also mis-scoped: the plan makes
the verifier lift a prerequisite "before iOS-A can start" — iOS-A never calls
the verifier; only iOS-B needs it.

**Corrections:** re-price iOS-0 at 2.5–3 weeks (or split verifier lift into
iOS-B's entry); move the verifier out of the iOS-A prerequisite path.

### F6 — minor — backup-exclusion "matching" claim elides the script's dual mechanism

`scripts/set-backup-exclusion.swift` sets `isExcludedFromBackup` *and falls
back* to a raw `com.apple.MobileBackup` xattr because host Foundation can
report the iOS-only key unsupported on Simulator containers (comment in the
script). In-app `URLResourceValues` under the simulated iOS runtime is the
right analogue, but the plan should state that the script's `check` mode
remains the CI oracle and must pass against app-downloaded installs (it accepts
either mechanism, so this likely holds — assert it, don't assume it).

### F7 — minor — iOS-C mischaracterizes what is being generalized

`catalog.ts:6,16` are **literal type annotations on the entry type**, not
"module-level constants"; the actual global pins are the hardcoded validator
expectations (`catalog.ts:72-99` — file_type 15, `gpt2`/`qwen2`, ChatML markers
— and `:165-171`), while `requiredMetadata` is *already per-entry data*. The
refactor is the validator + types + `models/catalog.json` schema +
`app.config.ts` embedding + `pocketlm_model.rb` + the M9 verifier's comparison
table. Substance right, mechanism misdescribed; the JSON source file is never
named.

### F8 — minor — omissions a competent implementer will hit

(a) **`app/src/app/bench.tsx`** — displays the single model's SHA (line 219);
per-model bench identity/results are unmentioned anywhere.
(b) **Protocol amendment for in-app publication**:
`INFERENCE_PROTOCOL_V2.md:285-301` frames publication as "Verified
provisioning" (host-driven); iOS-B changes *who publishes*. M6's amendment
covers Android wording only — the iOS in-app-install clause needs an explicit
amendment line in this plan, in both branches.
(c) **Where SHA-256 runs on iOS**: `storage.ts:229-233` deliberately avoids
rehashing 491 MB on the JS thread; hashing 1.12 GB must be native
(CommonCrypto in the downloader) — implied, never stated.
(d) Positive note: the qualification runner is parameterized by
`ReadyInstalledModel` (`runner.ts:85,777-786`), so "Release impact" correctly
covers it; `modelStorage.test.ts` / `qualificationRunner.test.ts` fixture churn
is covered by M8's "jest suites" inheritance.

## Verdict

**Safe to implement with the listed corrections.** The factual "current state"
section is the strongest part — every checked citation held. The weaknesses are
concentrated where the plan translates Android M9 mechanics into URLSession
reality (F2, F3) and in Simulator behavior of its own headline probe signal
(F1). No owner decision is violated; F1 actually *reinforces* decision 1 once
fixed.
